# 开发分支与交付策略

- 状态：建议采用
- 编写日期：2026-10-10

## 1. 是否需要单独拉分支

需要。后续开发不建议直接在 `main` 上进行。

原因：

1. 多租户改造涉及控制面、认证、存储、API、WebUI 和迁移，影响面较大。
2. 需要保持 `main` 随时可构建、可测试、可回滚。
3. 每个阶段都需要独立评审和验证。
4. 方便把高风险的权限和数据隔离改动拆成多个 PR。
5. 发生设计调整时，不会污染稳定主线。

当前仓库状态为干净的 `main`，因此适合从当前 `main` 创建功能分支。

## 2. 推荐分支策略

建议使用一个总功能分支，再按阶段拆 PR：

```text
main
  └── feature/multi-tenant-access-control
        ├── PR1 control-plane-foundation
        ├── PR2 identity-and-membership
        ├── PR3 workspace-runtime
        ├── PR4 route-authorization
        ├── PR5 webui-space-management
        └── PR6 migration-and-production-hardening
```

如果团队协作人数较多，也可以每个 PR 从总功能分支再创建短生命周期子分支：

```text
feature/multi-tenant-access-control
  ├── feat/control-plane-schema
  ├── feat/principal-context
  ├── feat/workspace-runtime
  ├── feat/api-authorization
  └── feat/webui-workspace-switch
```

不建议把所有代码直接堆到一个巨大 PR 中。

## 3. 推荐命名

总分支：

```bash
git switch -c feature/multi-tenant-access-control
```

子分支示例：

```bash
git switch -c feat/control-plane-schema
```

提交信息使用英文，例如：

```text
feat: add multi-tenant control-plane schema
feat: resolve workspace context from membership
feat: enforce document permissions by workspace
```

## 4. 开发前检查

创建分支前确认：

```bash
git status --short --branch
git fetch origin
git log --oneline -5
```

确保：

- 当前工作区没有未提交修改。
- 分支基于最新的 `main`。
- 需求和技术方案已经评审。
- 每个 PR 的范围和测试目录已经确定。

## 5. PR 拆分建议

### PR1：控制面基础设施

目标：零业务行为变化。

包括：

- schema version
- tenants/users/workspaces/memberships 表
- canonical ID
- Principal/WorkspaceContext 类型
- 基础 repository 和约束
- 单元测试

### PR2：身份与成员关系

包括：

- 数据库用户
- legacy `AUTH_ACCOUNTS` 导入
- membership resolver
- token version
- `/me` 和 workspace 列表
- 认证与 membership 测试

### PR3：Workspace runtime

包括：

- WorkspaceRuntimeRegistry
- namespace builder
- JSON/PostgreSQL 后端隔离
- 初始化和迁移并发控制
- workspace isolation tests

### PR4：API 授权

包括：

- document/query/graph/pipeline context dependency
- 权限矩阵
- 管理 API
- 401/403/IDOR 测试
- 审计事件

### PR5：WebUI

包括：

- workspace 列表和切换
- 权限驱动导航
- 成员和角色管理
- 401/403 体验
- 切换时缓存清理和 stream 取消

### PR6：生产化

包括：

- 其他外部存储后端
- per-workspace migration ledger
- 多 Pod 约束
- 并发、性能和安全测试
- 部署和升级文档

## 6. 每个 PR 的完成标准

每个 PR 必须包含：

1. 变更说明和明确的非目标。
2. 相关单元或集成测试。
3. 跨 workspace 的负向测试。
4. 兼容性说明。
5. 数据迁移或回滚说明（如涉及数据结构）。
6. 运行过的测试命令和结果。
7. 风险与后续工作。

## 7. 合并原则

- 只有测试通过并完成评审后合并到 `main`。
- 不在未完成的功能分支上开启生产部署。
- 高风险数据迁移先提供 dry-run。
- 控制面 schema 和 RAG 数据迁移分开发布。
- 任何权限默认变化都必须在 PR 描述中明确说明。
- 若 `main` 有新提交，开发分支应先同步并重新运行受影响测试。

## 8. 推荐的实际操作

当前可以先执行：

```bash
git switch -c feature/multi-tenant-access-control
```

然后仅提交需求和方案文档，或先不提交，待评审通过后再开始 PR1。是否提交文档属于团队协作决定；如果需要让其他开发者基于文档工作，建议先提交一个只包含 `需求和方案/` 的文档 PR。
