# 多租户技术设计方案

- 状态：待评审
- 版本：v0.1
- 编写日期：2026-10-10

## 1. 设计目标

在保留 LightRAG 现有核心数据结构和 SDK 兼容性的前提下，建立完整的：

```text
身份认证 -> 租户/空间成员关系 -> 权限校验 -> WorkspaceContext -> RAG runtime -> 存储访问
```

设计必须防止以下问题：

- 把客户端 workspace header 当作授权依据。
- 把 JWT 中的 role claim 当作持久化权限。
- 并发请求中修改一个全局 `LightRAG.workspace`。
- 只保护上传接口而遗漏删除、扫描、重试、图谱写入和 pipeline 管理。
- 控制面 migration 与 RAG 数据 migration 相互混淆。

## 2. 总体架构

```text
                    ┌─────────────────────────┐
                    │        WebUI/API         │
                    └────────────┬────────────┘
                                 │
                    ┌────────────▼────────────┐
                    │ Auth + Principal Context │
                    └────────────┬────────────┘
                                 │
                    ┌────────────▼────────────┐
                    │ Membership + Permission │
                    └────────────┬────────────┘
                                 │
                    ┌────────────▼────────────┐
                    │   WorkspaceContext      │
                    └────────────┬────────────┘
                                 │
                    ┌────────────▼────────────┐
                    │ WorkspaceRuntimeRegistry│
                    └────────────┬────────────┘
                                 │
        ┌────────────────────────▼────────────────────────┐
        │ LightRAG runtime: KV / Vector / Graph / Status │
        └─────────────────────────────────────────────────┘
                                 │
                    ┌────────────▼────────────┐
                    │     Audit / Metrics      │
                    └─────────────────────────┘
```

控制面负责身份、资源和权限；数据面继续使用 LightRAG 的存储和 pipeline，但必须使用服务端已授权的 workspace 上下文。

```text

```

密码只保存 bcrypt 或既有安全密码 helper 的 hash，不保存明文。

### 3.3 workspaces

```text

slug

storage_namespace
status                  active/archived/deleting
created_by

```

约束：

```text
UNIQUE(tenant_id, slug)
UNIQUE(storage_namespace)
FOREIGN KEY tenant_id -> tenants.id
```

### 3.4 memberships

```text
user_id
tenant_id
workspace_id           nullable when tenant-level membership
role_id
status
created_at
expires_at

```

建议建立唯一约束：

```text
UNIQUE(user_id, workspace_id)
```

并确保 workspace 属于 membership 中的同一 tenant。

## 4. Schema migration

现有 `storage_migrations.py` 负责 LightRAG 数据迁移，不等同于控制面数据库 schema migration。建议新增独立的：

```text
lightrag_control_schema_version
migration registry
migration lock
```

迁移要求：

- 版本化。
- 幂等。
- 可恢复。
- 失败时不改变已确认的数据归属。
- 支持 dry-run。
- 记录开始时间、结束时间、错误和重试次数。

RAG 数据迁移继续按 workspace 执行并记录 migration ledger，不要在服务启动时无条件扫描并阻塞所有租户。

## 5. Principal 和 WorkspaceContext

建议新增不可变数据类型：

```python
@dataclass(frozen=True)
class Principal:
    subject_id: str
    auth_method: str
    tenant_ids: tuple[str, ...]
    scopes: frozenset[str]

@dataclass(frozen=True)
class WorkspaceContext:
    tenant_id: str
    workspace_id: str
    storage_namespace: str
    permissions: frozenset[str]
    principal: Principal
```

请求处理流程：

```text
combined_auth
  -> get_current_principal
  -> resolve_workspace
  -> membership lookup
  -> require_permission
  -> WorkspaceContext
```

`role` 可作为兼容信息或查询结果展示，但不能替代 membership 查询。

## 6. Workspace Runtime Registry

当前服务启动时创建一个固定 `LightRAG` 实例。多租户模式下引入：

```text
WorkspaceRuntimeRegistry
  canonical_workspace_id -> LightRAG runtime
```

职责：

- 按 workspace 惰性创建实例。
- 对同一 workspace 的初始化去重。
- 调用 `initialize_storages()`。
- 管理 `check_and_migrate_data()` 生命周期。
- 限制实例数量和内存使用。
- 支持空闲 runtime 回收和优雅关闭。
- 将锁、pipeline、ingress、cache 保持在 workspace 范围内。

禁止：

```python
rag.workspace = request_workspace
```

因为并发请求会覆盖彼此的 workspace。

## 7. Namespace 设计

显示名称、slug 和实际存储 namespace 分离：

```text
workspace_id:        不可变内部 ID
workspace_slug:      用户可读、租户内唯一
storage_namespace:   服务端生成、不可变、用于数据后端
```

统一 namespace builder 负责生成：

- 文件目录
- Redis key prefix
- OpenSearch index 名称
- Qdrant payload 过滤值
- PostgreSQL workspace 条件
- shared storage final namespace
- cache identity

非法 workspace 标识应拒绝，而不是把多个不同字符串静默替换成同一个值。

## 8. API 接入策略

管理 API 与 RAG API 分开：

```text
/api/tenants
/api/workspaces
/api/workspaces/{workspace_id}/members
/api/workspaces/{workspace_id}/credentials
/api/workspaces/{workspace_id}/audit-events

/api/workspaces/{workspace_id}/documents
/api/workspaces/{workspace_id}/query
/api/workspaces/{workspace_id}/graph
/api/workspaces/{workspace_id}/pipeline
```

所有 document、query、graph、pipeline 路由必须：

1. 通过统一 context dependency。
2. 不能让 body 中的 workspace 覆盖 context。
3. 在业务操作前完成 permission check。
4. 使用对应 workspace runtime。
5. 按要求记录审计。

健康检查保持 liveness 兼容，但敏感配置和空间信息必须经过认证和授权控制。

## 9. WebUI 设计

登录成功后调用 `/me` 或 `/auth/context` 获取：

```json
{
  "user": {},
  "tenants": [],
  "workspaces": [],
  "active_workspace": {},
  "permissions": []
}
```

前端状态新增：

```text
principal
spaces
activeSpace
permissions
```

切换空间时：

1. 取消进行中的 query stream。
2. 清理文档、图谱、检索历史和 pipeline 状态缓存。
3. 更新请求上下文。
4. 重新获取 health/status 和当前空间数据。
5. 对 401 和 403 分别显示登录失效和权限不足。

前端根据权限隐藏按钮只能改善体验，不能替代后端授权。

## 10. 兼容策略

- 保留 `LightRAG(workspace=...)` 的 SDK 行为。
- 新增 dataclass 字段放在末尾或使用 keyword-only，避免破坏 positional compatibility。
- 旧 `AUTH_ACCOUNTS` 作为 bootstrap/legacy fallback，逐步迁移到 users。
- 旧 `WORKSPACE/--workspace` 映射为 legacy tenant/default workspace。
- 保留 `X-New-Token`、API prefix 和双 WebUI entry 行为。
- 多租户 enforcement 通过显式 feature flag 或部署模式启用。
- 新模式默认拒绝未授权跨空间访问。

## 11. 推荐 PR 顺序

1. 控制面 schema/version、canonical ID、Principal/Context 类型，零行为变化。
2. legacy auth 导入、membership resolver、`/me` 和 workspace 列表。
3. WorkspaceRuntimeRegistry、namespace builder，先覆盖 JSON/PostgreSQL。
4. document/query/graph/pipeline 全路由授权和管理 API。
5. WebUI 空间切换、成员/角色/API key/审计页面。
6. 外部 backend、migration ledger、多 Pod 约束、性能和安全审计。

## 12. 关键风险

| 风险 | 防护 |
|---|---|
| 信任 workspace header | 服务端 membership + permission 校验 |
| 信任 JWT role | role 只做兼容信息，权限从数据库计算 |
| 修改全局 RAG workspace | WorkspaceRuntimeRegistry，每空间独立 runtime |
| 存储 namespace 碰撞 | canonical opaque ID + 统一 namespace builder |
| pipeline/lock 串空间 | 所有 key、锁、状态带 workspace |
| token 长期有效 | token_version、撤销策略、禁用用户检查 |
| 启动迁移阻塞全部空间 | schema migration 与 workspace migration 分离、后台按空间执行 |
