# 控制面数据库设计

- 状态：待评审
- 版本：v0.1
- 日期：2026-10-10
- 适用范围：LightRAG 多租户、多用户和 workspace 权限管理 MVP

## 1. 设计结论

### 1.1 控制面与数据面分离

多租户模式增加一个 PostgreSQL 控制面，用来管理：

- 用户身份和账号状态。
- Tenant 与 Workspace 元数据。
- 用户成员关系和角色。
- API credential 的 hash、scope、吊销状态。
- 权限变更和敏感业务操作审计。
- 控制面 schema 与逐 workspace 数据迁移版本。

LightRAG 数据面继续由当前配置的 KV、vector、graph、doc-status 等存储后端承载。**MVP 不要求把文档、图谱、向量或 LLM cache 迁入控制面数据库。** 每次业务请求先在控制面解析身份和 workspace 授权，再使用获准 workspace 的 RAG runtime 和 storage namespace。

### 1.2 PostgreSQL 部署方式

- 多租户模式将 PostgreSQL 作为控制面必需依赖；单机 legacy 模式仍可按既有配置运行。
- 默认允许控制面与 RAG 数据面 PostgreSQL 部署在同一个 PostgreSQL cluster/database 服务中，但使用独立 schema、独立连接配置和独立迁移版本。若运维需要，也允许控制面使用独立 PostgreSQL 服务。
- 推荐控制面 schema 名为 `lightrag_control`；RAG 数据面继续由现有 backend 的表、namespace 和 workspace 机制管理，不移动到控制面 schema。
- 不把账户权限表混入现有图、向量、文档或 doc-status 表，也不通过修改已有 RAG 表来承载 membership。
- SQLite/JSON 不作为多用户生产控制面存储；可以用于未来专门实现并验证的本地开发 adapter，但不属于 MVP 的生产支持范围。

同一服务部署不代表逻辑耦合：控制面可以用单独的数据库 URL/连接池，即使 URL 指向同一数据库服务，也必须使用独立 schema 和 migration runner。

## 2. 领域关系

```text
Tenant 1 ─── N Workspace
User   N ─── N Tenant       via tenant_memberships
User   N ─── N Workspace    via workspace_memberships
Role   N ─── N Permission   via role_permissions
Workspace 1 ─── N API Credential
User/Service 1 ─── N Audit Event
Workspace 1 ─── N Migration Ledger entry
```

Tenant membership 用于组织级身份和未来组织管理；workspace membership 是访问 RAG 数据的最终授权关系。MVP 任何 workspace 数据访问都必须验证 active workspace membership 并具备对应 permission；仅有 tenant membership 不自动授予所有 workspace 的数据访问权。

## 3. 命名、主键和时间约定

- 主键使用 UUID（建议 UUIDv7；若项目可用依赖/运行时暂不支持，则 UUIDv4），作为不可变内部 ID。
- `slug` 是用户可读标识，不是存储隔离主键；唯一性按 tenant 范围定义。
- `storage_namespace` 为服务端生成的不可变标识，不使用 display name 或原始 slug 直接构造文件路径。
- 时间统一保存 `TIMESTAMPTZ`，应用层使用 UTC。
- 生命周期状态使用受约束的文本/枚举值；删除优先软删除或先进入 `deleting`，物理清理由可恢复任务完成。
- 所有外部输入在控制面规范化后再验证唯一性；不通过替换非法字符制造静默 slug 碰撞。

## 4. 核心表设计

以下为逻辑 schema；最终 SQLAlchemy/SQL DDL 类型与项目依赖确认后定稿。所有表位于 `lightrag_control` schema。

### 4.1 `tenants`

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | UUID | PK |
| `slug` | VARCHAR(100) | 全局唯一，规范化后存储 |
| `display_name` | VARCHAR(200) | 必填 |
| `status` | VARCHAR(20) | `active`, `suspended`, `deleting` |
| `settings_json` | JSONB | 仅受控的组织设置，不放密钥 |
| `created_by` | UUID | FK users.id，可为空用于系统 bootstrap |
| `created_at` | TIMESTAMPTZ | 必填 |
| `updated_at` | TIMESTAMPTZ | 必填 |
| `version` | INTEGER | 乐观并发版本，默认 1 |

约束：`UNIQUE(slug)`；`CHECK(status IN (...))`。

### 4.2 `users`

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | UUID | PK |
| `username` | VARCHAR(150) | 全局唯一、规范化 |
| `email` | VARCHAR(320) | 可空；非空时全局唯一，应用兼容大小写规范化 |
| `password_hash` | VARCHAR(255) | 必填；绝不保存明文 |
| `status` | VARCHAR(20) | `active`, `disabled`, `locked`, `pending` |
| `token_version` | INTEGER | 默认 1；撤销既有 token 的版本栅栏 |
| `last_login_at` | TIMESTAMPTZ | 可空 |
| `created_at` | TIMESTAMPTZ | 必填 |
| `updated_at` | TIMESTAMPTZ | 必填 |

认证仍需使用安全密码 helper。修改密码、禁用用户或全局撤销会话时递增 `token_version`；验证 token 时必须比较数据库中的当前版本，不能只信任 JWT claim。

### 4.3 `workspaces`

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | UUID | PK |
| `tenant_id` | UUID | FK tenants.id |
| `slug` | VARCHAR(100) | tenant 内唯一 |
| `display_name` | VARCHAR(200) | 必填 |
| `storage_namespace` | VARCHAR(100) | 全局唯一、不可变、服务端生成 |
| `status` | VARCHAR(20) | `active`, `archived`, `deleting`, `failed` |
| `created_by` | UUID | FK users.id |
| `created_at` | TIMESTAMPTZ | 必填 |
| `updated_at` | TIMESTAMPTZ | 必填 |
| `version` | INTEGER | 默认 1 |

约束与索引：

- `UNIQUE(tenant_id, slug)`。
- `UNIQUE(storage_namespace)`。
- `UNIQUE(tenant_id, id)`，供复合外键确保 tenant/workspace 归属一致。
- `(tenant_id, status)` 索引。

### 4.4 `tenant_memberships`

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `tenant_id` | UUID | FK tenants.id |
| `user_id` | UUID | FK users.id |
| `role_code` | VARCHAR(40) | MVP 固定枚举/系统角色 |
| `status` | VARCHAR(20) | `active`, `invited`, `suspended`, `removed` |
| `created_by` | UUID | FK users.id，可空用于 bootstrap |
| `created_at` | TIMESTAMPTZ | 必填 |
| `expires_at` | TIMESTAMPTZ | 可空 |
| `updated_at` | TIMESTAMPTZ | 必填 |

主键：`PRIMARY KEY(tenant_id, user_id)`。索引：`(user_id, status)`。

### 4.5 `workspace_memberships`

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `workspace_id` | UUID | FK workspaces.id |
| `tenant_id` | UUID | 与 workspace 组合校验 |
| `user_id` | UUID | FK users.id |
| `role_code` | VARCHAR(40) | `owner`, `admin`, `editor`, `viewer` |
| `status` | VARCHAR(20) | `active`, `invited`, `suspended`, `removed` |
| `created_by` | UUID | FK users.id |
| `created_at` | TIMESTAMPTZ | 必填 |
| `expires_at` | TIMESTAMPTZ | 可空 |
| `updated_at` | TIMESTAMPTZ | 必填 |

主键：`PRIMARY KEY(workspace_id, user_id)`。复合外键：`(tenant_id, workspace_id) -> workspaces(tenant_id, id)`。索引：`(user_id, status)`、`(tenant_id, workspace_id, status)`。

每个 active workspace 必须保持恰好一个 active owner；转让 owner 应在单个事务中完成。MVP 的权限由固定 `role_code -> permission set` 程序映射产生，避免角色表/权限表过早增加写入面；数据库保留后续自定义角色升级路径。自定义角色不属于 MVP。

### 4.6 `api_credentials`

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | UUID | PK |
| `tenant_id` | UUID | FK tenants.id |
| `workspace_id` | UUID | MVP 必填，FK workspaces.id |
| `name` | VARCHAR(150) | 用户提供的显示名 |
| `key_prefix` | VARCHAR(16) | 用于识别，不是秘密 |
| `key_hash` | VARCHAR(255) | 唯一，使用适合高熵 token 的安全 hash/HMAC 方案 |
| `scopes` | JSONB | 只允许白名单 permission scope |
| `status` | VARCHAR(20) | `active`, `revoked`, `expired` |
| `expires_at` | TIMESTAMPTZ | 必填或按安全策略设置期限 |
| `revoked_at` | TIMESTAMPTZ | 可空 |
| `created_by` | UUID | FK users.id |
| `last_used_at` | TIMESTAMPTZ | 可空 |
| `created_at` | TIMESTAMPTZ | 必填 |

复合外键确保 `(tenant_id, workspace_id)` 对应同一 workspace。明文 credential 仅在创建响应返回一次；任何列表/日志不得回显明文。

### 4.7 `audit_events`

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | UUID | PK |
| `tenant_id` | UUID | 可空，仅适用于平台级事件 |
| `workspace_id` | UUID | 可空，仅适用于 tenant/platform 事件 |
| `actor_user_id` | UUID | 可空，系统任务使用 `actor_type` 标记 |
| `actor_type` | VARCHAR(20) | `user`, `api_credential`, `system`, `platform_admin` |
| `action` | VARCHAR(100) | 稳定动作名，如 `document.delete` |
| `resource_type` | VARCHAR(100) | 可空 |
| `resource_id` | VARCHAR(200) | 可空 |
| `request_id` | VARCHAR(100) | 关联请求日志 |
| `result` | VARCHAR(20) | `success`, `denied`, `failure` |
| `ip` | INET | 可空；遵循代理信任配置 |
| `metadata_json` | JSONB | 仅写非秘密、最小必要字段 |
| `created_at` | TIMESTAMPTZ | 必填 |

审计记录对应用账号只允许 INSERT/受控查询，不允许普通业务路径 UPDATE/DELETE。禁止记录密码、token、完整 API key、文档正文或不必要的个人信息。应定义保留期和归档策略。

### 4.8 `control_schema_versions`

| 字段 | 类型 | 说明 |
|---|---|---|
| `version` | INTEGER | PK，已应用版本 |
| `migration_id` | VARCHAR(150) | 唯一迁移标识 |
| `checksum` | VARCHAR(128) | 检测已应用 migration 文件是否被改写 |
| `applied_at` | TIMESTAMPTZ | 必填 |
| `execution_ms` | BIGINT | 执行耗时 |

只在数据库创建/升级控制面 schema 时更新。通过 PostgreSQL advisory lock 或单独 migration lock 避免并行实例重复升级。

### 4.9 `workspace_migration_ledger`

| 字段 | 类型 | 说明 |
|---|---|---|
| `workspace_id` | UUID | FK workspaces.id |
| `migration_id` | VARCHAR(150) | workspace 级数据迁移标识 |
| `status` | VARCHAR(20) | `pending`, `running`, `succeeded`, `failed` |
| `attempt` | INTEGER | 尝试次数 |
| `started_at` | TIMESTAMPTZ | 可空 |
| `finished_at` | TIMESTAMPTZ | 可空 |
| `error_code` | VARCHAR(100) | 可空；不存秘密或完整原始敏感异常 |
| `details_json` | JSONB | 可恢复的非敏感进度信息 |

主键：`PRIMARY KEY(workspace_id, migration_id)`。它记录按空间运行的 RAG 数据迁移，不替代 LightRAG 现有 `_StorageMigrationMixin`；具体哪些迁移进入 ledger 要在实现 PR 中逐项定义。

## 5. 事务和一致性边界

1. Tenant、workspace 和 membership 元数据变更在控制面数据库事务中完成。
2. 创建 workspace 时，先在事务中创建 `provisioning` 状态记录和 owner membership；随后初始化 RAG runtime；初始化成功后转为 `active`。失败时保留可重试状态，不留下可被业务路由访问的半初始化空间。
3. 控制面事务与 RAG 多存储写入之间没有分布式事务。跨存储流程使用明确状态、幂等操作和可恢复任务，遵循项目现有的 consistency-without-transactions 合同；不得把一次数据库事务误认为同时覆盖图、KV、vector 和文件存储。
4. 删除 workspace 先转为 `deleting` 并拒绝新业务访问，再执行逐空间清理；只有清理完成才标记 `deleted`/移除元数据。失败必须可以续跑，不能提前删掉归属信息。
5. 移除成员、降权或禁用用户要确保后续请求重新校验当前 membership/token version；不能依赖长寿命 JWT 中的旧 permission 列表。

## 6. 连接配置与运行方式

新增独立控制面配置，例如：

```text
LIGHTRAG_CONTROL_DATABASE_URL
LIGHTRAG_CONTROL_DATABASE_SCHEMA=lightrag_control
LIGHTRAG_MULTI_TENANT_ENABLED=false
```

最终配置名须遵循项目现有 config/环境变量命名习惯，并同步 `env.example`、CLI/help 和配置测试。

运行原则：

- `LIGHTRAG_MULTI_TENANT_ENABLED=true` 时，控制面 URL 必须配置且启动健康检查通过，否则服务启动失败并给出明确配置错误；不能静默退化为无授权模式。
- flag 关闭时，保留现有单 workspace 运行行为，不要求额外数据库。
- 控制面使用独立连接池、连接生命周期、超时和健康状态；不得复用每请求可变的 tenant/schema/search_path。
- 连接 URL、密码和密钥不能写入日志或 audit metadata。
- 同 cluster 部署仍建议用最小权限数据库用户；migration role 与 runtime role 可分离。Runtime role 不应有任意 DDL 权限。

## 7. Migration 策略

### 7.1 控制面 schema migration

新增独立版本化 migration registry。每个版本文件只做一个不可变升级，migration 一旦发布不原地修改；修正通过新版本迁移完成。执行要求：

1. 启动时在 feature enabled 模式下检查数据库连接和 schema 版本。
2. 生产环境建议提供显式 `lightrag-control-migrate` 管理命令；是否允许 web worker 自动迁移通过部署配置明确，默认避免多个 worker 同时 DDL。
3. 使用 advisory lock 或单执行者机制串行应用 schema migration。
4. Migration 记录版本、checksum、耗时和错误；失败后保留旧 schema，不允许标记为成功。
5. 支持备份/恢复演练和向前修复；不承诺所有 DDL 都能无损自动 downgrade。

### 7.2 Legacy 用户与 workspace 导入

- 导入 `AUTH_ACCOUNTS` 时仅在显式启用 bootstrap/import 时运行；不得把明文密码复制进控制表或日志。按现有安全密码 helper 重新生成 hash。
- 导入必须幂等：以规范化 username 和来源标识去重，重复执行不新增重复用户或 membership。
- legacy `WORKSPACE/--workspace` 映射为一个 legacy tenant 和 default workspace，`storage_namespace` 必须固定映射并先验证现有数据路径/后端值。
- 导入前提供 dry-run，显示将创建的账号数、默认 tenant/workspace 和可能冲突；导入失败时 legacy 服务行为保持不变。
- 不自动推断未知用户之间的数据所有权。无法证明的数据归属必须停下并要求管理员决策，禁止猜测后迁移。

### 7.3 RAG workspace migration

按 workspace 运行并写 `workspace_migration_ledger`；支持失败重试、续跑和 per-workspace 备份/验证。复用现有 LightRAG migration contract，但不把控制面 schema 迁移塞入 `storage_migrations.py`。

## 8. 数据库安全要求

- 所有 SQL 必须参数化；动态 schema/table 标识只能来自固定配置白名单，不允许直接使用请求输入。
- 所有租户资源查询都按已授权 `tenant_id/workspace_id` 过滤；必要时再评估 PostgreSQL RLS，但 RLS 不替代应用授权。
- 对 `workspace_id` 和 `tenant_id` 的组合使用复合外键，防止跨 tenant 错配。
- 密码 hash、credential hash、token、数据库连接串不进入普通日志。
- API credential 使用高熵随机生成值；存储 keyed hash 或适合高熵秘密的不可逆验证值，并采用可轮换服务器 pepper/密钥管理策略。
- 查询审计只记录必要元数据；默认不记录用户查询全文、文档正文和 LLM 输出。
- 对分页、审计检索和成员列表设置上限与索引，避免无界查询。

## 9. 测试要求

### Schema / repository

- 表、唯一约束、外键、CHECK 和复合 tenant/workspace 约束。
- 重复 slug、重复 membership、孤儿 workspace、跨 tenant workspace membership 必须失败。
- username/email 规范化和唯一约束行为。
- owner 转让事务保证始终恰好一个 active owner。

### Migration

- 空库创建到最新版本。
- 每个版本重复运行不重复副作用。
- migration checksum 不一致时 fail closed。
- 并发启动只有一个 migration runner 生效。
- 中断/失败后可恢复，不把失败标为成功。
- legacy import dry-run、幂等重复导入和冲突拒绝。
- 指定 workspace 的 migration 不触碰其他空间。

### API / 安全

- user A 对 user B 的 workspace membership 查询失败。
- 伪造 header/URL/body workspace 不能改变已授权 context。
- 禁用账号/token version 变更后旧 token 失效。
- revoked/expired API credential 不能认证；scope 不可超出绑定 workspace。
- audit 不含秘密和正文。

## 10. 尚待评审的决策

以下选项不在当前文档中假装已经定案，进入 PR1 前需要确认：

1. 在现有依赖与迁移实现约束下，控制面采用 SQLAlchemy Core/ORM、asyncpg 直连，还是项目已有数据库访问抽象。
2. schema migration 采用 Alembic，还是项目内轻量、版本化的 SQL runner；必须检查项目依赖和部署方式后决定。
3. UUIDv7 是否由依赖提供，或先用 UUIDv4。
4. 多租户模式中 tenant membership 与 workspace membership 的默认继承规则；本设计默认只有 workspace membership 授予数据访问。
5. owner/admin 能否创建 API credential，credential 的默认 scope 和最长有效期。
6. 生产环境 schema migration 是部署前显式命令，还是单实例启动时执行。
7. 控制面与 RAG PostgreSQL 是否共享 database/schema owner；本设计默认同 cluster 可用、schema 和连接角色隔离。

这些决策需要在数据库实现 PR 前通过 ADR/评审定稿，避免 ORM、migration tool 或账号兼容机制成为隐式架构决定。

## 11. 实施拆分

### DB-PR1：控制面 schema 与连接基础

- 配置/连接生命周期。
- `lightrag_control` schema 和 schema version runner。
- `tenants`、`users`、`workspaces`、两类 memberships。
- repository 与约束测试。
- 不改变既有 API 登录和 RAG 行为。

### DB-PR2：认证凭据和审计

- API credentials。
- token version 校验。
- audit events 写入接口和脱敏测试。

### DB-PR3：bootstrap 与逐空间迁移 ledger

- legacy 单空间导入 dry-run/执行。
- workspace migration ledger。
- 失败恢复和重启测试。

每个 PR 依项目指南仅运行改动模块对应测试；如修改 WebUI，再执行完整 Bun 测试、TypeScript 检查和 lint。
